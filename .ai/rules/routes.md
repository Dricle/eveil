# Routes

## The app opens inside a project: current project is the `{project:slug}` URL segment, never session
Everything below the dashboard belongs to one project, so the project is named in the URL rather than carried in session: `Route::prefix('{project:slug}')` wraps the whole authenticated app (everything that used to sit behind `project.require`) in `routes/app.php`. A save must only ever be able to reach the project the loaded page actually shows, even when a different browser tab or a stale session disagrees - that used to not hold: session is shared across every tab, and a save trusting it let a save made in one tab silently land on whatever project a DIFFERENT tab had switched to. `.ai/rules/models.md`'s "leaking data across projects is the worst bug this app can have" is exactly the bug this design closes.

One middleware, aliased in `bootstrap/app.php`, on the `{project:slug}` group only:
- `project.set` (`SetCurrentProject`). Reads the already-bound `Project` off the route (`$request->route('project')`), authorizes it (`Gate::authorize('view', $project)` - 404, not a silent fallback, via `ProjectPolicy::view()`'s `denyAsNotFound()`), assigns `CurrentProject`, binds `URL::defaults(['project:slug' => $project->slug])` so the rest of this request's own `route()`/`to_route()` calls don't need to repeat it, and writes `session('current_project_id')` as a "last visited" HINT ONLY - read back solely by `AppHomeController` (the bare `/app` entry point) to pick a default, never re-read here as authority over which project a request acts on. This is also the one place HTTP sets `CurrentProject`, which is what makes the `BelongsToProject` scope constrain queries.

There is no `project.require` any more: a URL naming no project simply cannot match a route inside `{project:slug}`, so there is nothing left to require. The bare `/app` entry point (`AppHomeController`, named `app.home` - NOT `home`, which `routes/web.php` already owns for the marketing site's root) does what `project.require` used to: picks the hinted project, falls back to the first one this user can see, else redirects to `projects.create`.

**`Route::bind('project', ...)` (`app/Providers/AppServiceProvider.php`) is load-bearing, not optional.** No controller behind `{project:slug}` type-hints a `Project $project` parameter (they all read `CurrentProject::getOrFail()` instead), and Laravel's IMPLICIT route-model binding only fires when a controller action asks for the model - without the explicit `Route::bind()`, `{project:slug}` never resolves past a raw string. Confirmed the hard way: it silently passed the slug string into `Gate::authorize()`, which denied everything with a generic 403 instead of evaluating the policy.

**`SetCurrentProject` calls `$request->route()->forgetParameter('project')` after consuming it - do not remove this.** Every controller behind `{project:slug}` was written for a world where its OWN resource (`Company $company`, `int $campaign`, `LinkedinAccount $linkedinAccount`...) was the only route parameter, and Laravel's `ControllerDispatcher` ultimately binds arguments by POSITION (`Controller::callAction()` ends in `array_values($parameters)` right before the call - see `vendor/laravel/framework/.../ResolvesRouteDependencies.php`). Leaving `project` in the route's parameter bag shifts every later parameter one slot right and hands the controller a `Project` where it expects its own model - a `TypeError` at best, a wrong-argument silently-accepted value at worst. `forgetParameter()` is what keeps every existing controller signature correct, unchanged.

Controllers still read `CurrentProject::getOrFail()`, which throws rather than returning null. That is what lets them be typed without re-testing what the middleware guarantees, and it did not need to change: `CurrentProject` is populated the same way as before, just sourced from the route instead of session.

Trap, unchanged: `HandleInertiaRequests` is in the `web` group and therefore runs BEFORE route middleware, so a shared prop that reads `CurrentProject` must be a CLOSURE. A plain value resolves one request too early and serves the previous request's project.

**`URL::defaults()` must be keyed `project:slug`, not `project`.** Laravel only recognises a default for a custom-keyed implicit binding (`{project:slug}`) under `<name>:<bindingField>` - a plain `project` key is silently never matched, and a `route()` call passing a second positional parameter (`route('companies.status', $company)`) then consumes that positional value for `project` instead of `company`. `SetCurrentProject`, `tests/Pest.php`'s `forProject()` helper, and `tests/TestCase.php`'s `actingAs()` override all key it this way - keep them in step if this ever changes.

Project settings live under `/app/{project}/settings/*` (`settings.project.*`, `settings.knowledge-base.*`), not `/app/projects/{id}/...`. There is no switcher route any more (`current-project.update` is gone, along with `CurrentProjectController`): switching projects is a plain client-side navigation (`resources/js/lib/switchProjectUrl.ts`) that rewrites the URL's `{project}` segment and lets the normal request cycle re-resolve everything - no server-side mutation involved.

## Reserved top-level slugs
Literal path segments registered as siblings of `{project:slug}` (`projects`, `organizations`, `app-settings`, `account`, `setup`, `invitations`) cannot be a project's slug, or a URL to that literal route would be ambiguous with a project dashboard. Enforced in `App\Models\Project::slugExists()`, which treats them as already-taken so `HasSlug`'s normal `-2`/`-3` suffix loop routes around the collision - no separate validation path. If a new top-level literal route is ever added outside `{project:slug}`, add its segment to `Project::RESERVED_SLUGS` too.

One consequence worth knowing, not a bug: a single-segment path under `/app/` that matches no literal route (e.g. `/app/register` when Fortify registration is disabled) falls through to `GET /app/{project:slug}` (the `dashboard` route) rather than 404ing directly. A guest still can't get in - the `auth` middleware redirects to login before the (nonexistent) project slug is even looked up - but the response is a 302, not a 404. `tests/Feature/AuthTest.php`'s "does not register the sign-up routes when sign-ups are closed" test documents this exactly.
